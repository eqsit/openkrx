### Подтверждённые ветки BlatantAgent и привязки настроек

Из корректно декомпилированного `0x1402d2080`:

1. Копируется текущий `CNetObj_PlayerInput` (40 байт) активного локального игрока.
2. Если Auto Drag выключен после автоматического hook, hook сбрасывается.
3. Клонируется predicted world и проверяется наличие локального персонажа.
4. Вызываются предобработка aim/track (`0x1402d4460`), две ранние проверки (`0x1402d1b90`, `0x1402d1e10`).
5. Иначе `0x1402d30b0` получает `Check Ticks` (global 0x1405e498c).
6. При score/sentinel 9999 найденная последовательность сохраняется, возвращается первый input.
7. При отсутствии полной безопасной последовательности NSIF разрешает повторно проверить хвост **предыдущей** последовательности (со второго input); только если симуляция подтверждает весь хвост, берётся этот input и удаляется из сохранённого плана.
8. Без результата и допустимого fallback возвращается `std::optional` без значения. Это не означает нулевой ввод: вызывающая обвязка ещё должна быть проверена.

Адреса настроек сверены с кодом регистрации и строками из того же образа:

- Check Ticks: `0x1405e498c`, default 26.
- Direction/Hook: `0x1405e4990` / `0x1405e4994`, оба default 1.
- Blatant teles/death/unfreeze: `0x1405e4998` / `0x1405e499c` / `0x1405e49a0`, default 0.
- Blatant unfreeze ticks: `0x1405e49a4`, default 26.
- Aimbot/FOV: `0x1405e49a8` / `0x1405e49ac`, default 0/90.
- Auto Aim/Aim Assist/Segments: `0x1405e49cc` / `0x1405e49d0` / `0x1405e49d4`, defaults 0/1/5.
- Safe tracking/Auto Drag/Track Points: `0x1405e49d8` / `0x1405e49dc` / `0x1405e49e0`, defaults 0/0/0.
- NSIF/Kick in/Player prediction: `0x1405e49e4` / `0x1405e49e8` / `0x1405e49ec`, defaults 1/26/1.

Машиночитаемая полная привязка: `research/rea/config-addresses.json`.
Число настроек не доказывает семантику каждого флага; продолжать трассировать consumers.

### Ещё одна серия результатов REA

`022-blatant-search-and-guards.json`: 6/6 функций успешно декомпилированы.
`023-blatant-candidates-and-workers.json`: 4/4; `024-blatant-actions-simulation.json`: 10/10.

- `0x1402d30b0` собирает приоритетные начальные действия, распределяет независимые поиски по thread pool, после ожидания берёт **первый в исходном порядке** результат с 9999; если такого нет — сортирует результаты по убыванию survival score и берёт непустой лучший при score>0. Это не старый самодельный beam search.
- Генератор `0x1402d2a90` меняет направление и hook, **jump принудительно равен 0** через `0x1402ccd60`. Группы разделены sentinel-записями; порядок зависит от направления и hook исходного ввода. Нельзя добавлять jump в пространство поиска и называть это исходным алгоритмом.
- `0x1402d2490` сначала оценивает constant-input survival для действий группы, сортирует её, выбирает лучший и удаляет дубликаты по паре (Direction, Hook). Дополнительно добавляет варианты aim, если включён внутренний aimbot.
- `0x1402cd640` симулирует цикл **0..CheckTicks включительно** (CheckTicks+1 шаг), вызывает DirectInput → ++GameTick → PredictedInput → World.Tick, возвращает индекс первого freeze либо 9999. Границу цикла сохранить при переносе.
- `0x1402cd750` — обнаружение выхода из freeze на TILE_UNFREEZE (11) с мутацией переданного клона мира; вызывается только при соответствующем флаге.
- `0x1402d4460` обновляет точку hook tracking и при Safe Aim Tracking проверяет её отдельным поиском.
- После перезагрузки прямые `mcp__rea__*` инструменты появились в агенте. `binary_session` реально вызван через Codex, identity=aligned, client=codex-mcp-client 0.165.0. Успешно подключение, а не только регистрация.

В `026` три адреса leaf-thunk не распознаны Ghidra как функции. Это не отсутствие кода:
`objdump` показывает jump-thunks; по vtable найден переход к `0x1402d0dc0`.
Shell-disassembly здесь обозначается именно как shell-наблюдение, не REA Evidence.
Не повторять те же неизвестные адреса: разбирать установленные jump targets.

Существенные места для проверки перед интеграцией:

1. В `0x1402d2490` Ghidra показывает два прохода по sentinel-группам, первый
   с накоплением scored actions, второй с очисткой после sentinel. Нынешний
   C++ `Candidates` реализует один проход. Сверить CFG/инструкции и исправить
   точный порядок, не объявлять кандидатов эквивалентными до проверки.
2. В `0x1402d1060` угловой внутренний scan на 50 проб пока перенесён по
   интерпретации (`angle + probe * step/50`); подтвердить math arguments по
   инструкциям. Сам псевдокод не всегда сохраняет float аргументы calls.
3. Auto-drag передаёт anchor, который выглядит как relative mouse aim, а
   Greedy позднее вычитает world position. Не «чинить» автоматически:
   проверить исходную семантику/возможную ошибку KRX.
4. `Direction/Hook` flags имеют xrefs только из регистрации/UI; до решения,
   что они инертны в 1.32, исключить overlapping-wide-load/indirect consumers.
5. Нужна изолированная копия CGameWorld: штатный CopyWorld связывает parent/child
   и инвалидирует существующий predicted copy. Нельзя портить настоящий мир
   или параллельно клонировать его таким способом из worker threads.
6. C++ не тестировался/не компилировался после записи. Не включать по умолчанию
   и не выдавать за завершающую сборку.

### Подтверждённый greedy (`0x1402d3d20`)

- Первый шаг использует переданный начальный input.
- На последующих шагах оценивает шесть constant-input вариантов в порядке
  `(0,0), (0,1), (1,0), (-1,0), (1,1), (-1,1)` по (direction,hook), jump=0.
- После первого варианта с survival > remaining horizon прекращает перебор.
- Иначе выбирает maximum survival, сохраняя исходный порядок равных вариантов.
- При безопасном suffix сохраняет remaining inputs без лишнего probe tick.
- На freeze возвращает индекс шага и только inputs до этого шага.
- При track anchor пересчитывает относительный aim к фиксированной точке.

### Баг: «сковывает на ровном месте» (2026-10-28)

Пользователь проверил сборку: Avoid блокировал движение на ровном месте и вёл
себя непредсказуемо (в KRX то же место проходится нормально).

Причина в моём `CBlatantPlanner::Decide`: replay сохранённого плана стоял
**до** проверки `Kick In Ticks`. После первого срабатывания план (до 26
инпутов) перезаписывал ввод игрока даже когда его собственный ввод был
полностью безопасен — отсюда ощущение «сковывает» и странные движения.

Исправлено:
- `Kick In Ticks` проверяется первым; если собственный ввод безопасен на этом
  горизонте, план очищается и ввод не трогается вообще;
- снимок мира теперь берётся из `m_PredictedWorld` (если в нём есть локальный
  персонаж), а не из `m_GameWorld`: predicted-мир уже содержит эффект прошлых
  инпутов и включает предсказание freeze;
- добавлена диагностика `openkrx_avoid_debug 1`: пишет в консоль решение,
  frozen-состояние, размер плана и время `Decide` (мс/мкс), предупреждает при
  `>20 ms`.

Добавлен регрессионный тест: после опасного мира безопасный ввод не должен
перезаписываться, план должен очищаться. Тесты: OK
(`research/deepseek/planner-tests.log`).

после фикса ещё не подтверждено пользователем.

- Teles/Death: флаги есть, поведения нет.
- ESP/Visuals: только конфиги и чекбоксы.
- Legit (1) и Fent (3) агенты не реализованы.
- Физика: эталон 18.9.1, база 20.3 — parity не доказан.
- Живой тест не покрывает: NSIF, unfreeze, aimbot, auto-drag, реальный обход
  freeze на настоящей карте.

### 4. Текущая гипотеза по «сбиваюсь везде»

1. Отсутствие гейта «стою на freeze-тайле» из координатора: бот вмешивается,
   когда ти уже в freeze.
2. NSIF может отдавать `plan[1]` из старого плана.
3. Копия мира содержит всех игроков (нет `0x1402cd0c0`) и не учитывает
   pre-inputs клиента → «безопасные» планы в реальности не безопасны.
4. Хук-кандидаты используют сырой прицел; в симуляции цепляются, в игре —
   дёргают.

Проверка этих гипотез поручена двум read-only субагентам: потребитель слота
`0x52a5c0` и проверки координатора; поиск `0x1402d30b0` + NSIF `0x1402cd350`.

### Поиск и NSIF: разбор по инструкциям (REA-субагент)

- Поиск `0x1402d30b0`: одна общая копия мира (`0x1402cd0c0`, с отсевом
  чужих/далёких тии), N кандидатов → N результатов, `results[i]` =
  `candidates[i]`, задачи раскладываются по пулу потоков (по числу ядер,
  fallback 8), ожидание блокирующее.
- Победитель: если есть `status == 9999` — берётся **первый по индексу**,
  т.е. порядок кандидатов решает; иначе — сортировка по status по убыванию
  (introsort без tie-breaker) и первый; `status < 1` или пустой план → пустой
  результат и status −1.
- NSIF `0x1402cd350`: копия переданного снимка, проигрывание хвоста плана
  (без первого элемента), «плохой тик» через `0x1402cc900`; успех =
  число хороших тиков == длина хвоста; при успехе вызывающий стирает только
  `plan[1]`. Для агентов 0 и 2 предикат «плохо» — простой
  (`FreezeTime>0 || Deep || Live`), для 1 и 3 — расширенный with look-ahead.
  Значит для Blatant наш `Frozen()` эквивалентен, кроме трактовки смерти.

Правки порта по итогам:
- добавлен гейт координатора «стою на freeze-тайле (9) → не вмешиваться»;
- результат агента подставляется целиком (40 байт), как слот ввода KRX;
- `krx_avoidtileplayerprediction` теперь выбирает источник снимка
  (predicted-мир vs game-мир).

Осознанное расхождение: у нас нет пула потоков — поиск последовательный.
Победитель при нескольких 9999 у нас тоже «первый по порядку кандидатов»,
но при равных lifespan `std::sort` может дать другой порядок, чем introsort
MSVC (tie-breaker отсутствует в обоих).

### Критическая находка: куда KRX пишет решение (REA-субагент)

Слот `client+0x52a5c0+idx*0x28` — это штатное поле **`CControls::m_aInputData[g_Config.m_ClDummy]`**
(`CControls` лежит по `client+0x52A560`; `idx` = `cl_dummy`). То есть координатор
`0x1402cc620` пишет решение прямо в структуру ввода контролов.

Порядок в кадре:
`CClient::Update → GameClient()->OnUpdate (внутри — координатор) → SendInput →
OnSnapInput → CControls::SnapInput → упаковка NETMSG_INPUT`.

`SnapInput` — последний потребитель и он **перезаписывает**:
- `m_PlayerFlags` целиком;
- `m_TargetX/m_TargetY` из `m_aMousePos` (и sub-tick aiming);
- `m_Direction` из `m_aInputDirectionLeft/Right` (0/−1/+1).

Следствие: на провод из решения агента в этом билде попадают только
`m_Jump`, `m_Fire`, `m_Hook`, `m_WantedWeapon`, `m_NextWeapon`, `m_PrevWeapon`.
Направление и прицел всегда остаются за игроком/мышью.

Наш порт до этого писал ввод **после** `SnapInput`, поэтому реально менял
направление — это и есть «сбиваюсь». Добавлен режим:
- `openkrx_avoid_apply 0` (по умолчанию) — как в KRX: писать в
  `m_aInputData` до `SnapInput`, направление/прицел/флаги перетираются;
- `openkrx_avoid_apply 1` — прежнее поведение с полной подменой ввода.

Открытый вопрос: если в KRX направление не доходит до сервера, то «бот
подводит» должен объясняться другой веткой (мышь/аимбот) — это ещё не
доказано. До выяснения режим 1 оставлен как экспериментальный.

Прочие проверки координатора (подтверждено):
- гейт `FUN_1402b47c0`: `PLAYERFLAG_PLAYING` + `Client()->m_State == STATE_ONLINE`;
- `FUN_1402b47f0`: блокирует при отсутствии локального персонажа/спектаторе;
- `FUN_1402b4450`: блокирует, если ти уже frozen (`FreezeTime>0 || deep || live`);
- проверка тайла 9 (`TILE_FREEZE`) в точке ти — подтверждена инструкциями;
- AFK `0x1402cc7a0` — блок только по таймеру + зажатым A+D + неподвижной мыши.

## Вывод по опыту: KRX не рулит направлением (проверено дважды)

Проверил `CControls::SnapInput` не только в текущей базе 20.3, но и в
**18.9.1** (версия эталона KRX), файл взят из upstream:
`https://raw.githubusercontent.com/ddnet/ddnet/18.9.1/src/game/client/components/controls.cpp`.

В обеих версиях `SnapInput` делает одно и то же:
- `m_Direction = 0`, затем `-1`/`+1` из `m_aInputDirectionLeft/Right`
  (18.9.1: строки 239–243; 20.3: те же поля);
- `m_TargetX/Y` = `m_aMousePos` (и `m_aMousePosOnAction` при sub-tick aiming);
- `m_PlayerFlags` выставляются заново.

Координатор KRX `0x1402cc620` пишет решение в `CControls::m_aInputData`
**до** `SnapInput`. Значит и в эталонной 18.9.1 на провод из решения агента
попадают только **Jump, Fire, Hook, WantedWeapon, NextWeapon, PrevWeapon**.
Направление и прицел всегда остаются за игроком/мышью.

Отсюда вывод по опыту, а не по догадке:
1. «KRX подводит прекрасно» — это assistance (прыжок/хук/огонь в нужный
   тик) при твоём собственном рулении, а не автопилот.
2. Наш режим `openkrx_avoid_apply 1` (полная подмена после `SnapInput`) —

- Качество порта надо мерить по Jump/Hook/Fire (а не по «куда он меня

- Единственный способ доказать это окончательно — прогнать **сам эталон

Хук-овнершип (жалоба пользователя): автоматические хуки Avoid не должны

поэтому направление автоматического хука всегда оставалось за Avoid.

## 2026-11-01 — возврат оружия после rocket save

Пользователь попросил: после сейва автоматически убирать гранату и возвращать
оружие, которое стояло до сейва. Раньше сейв выставлял WantedWeapon=GRENADE+1
и оставлял гранату в руках.

Добавлен CRocketWeaponRestore (avoid/rocket_save.h): каждый тик запоминает
последнее негранатовое оружие (WantedWeapon, иначе активное оружие; ниндзя и
граната не годятся). Когда AdjustInput выбирает гранату, выбор помечается
временным (Begin, дедлайн 200 тиков). После этого, если сейв больше не просит
гранату и не висит отложенный release (m_ReleaseModulo), ввод уходит с
восстановленным оружием; когда персонаж реально переключился, состояние
снимается. Если игрок сам выбрал другое оружие — сейв не вмешивается.
Тело прежнего AdjustInput вынесено в AdjustInputCore, обёртка применяет
восстановление.
